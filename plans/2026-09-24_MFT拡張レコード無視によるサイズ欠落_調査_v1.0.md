# MFT拡張レコード無視によるサイズ欠落・名前の誤りの調査

## 不具合の記録（2026-09-24 報告）

- 現象: 管理者権限で `dist\QuickFolderSize_cli.exe C:\`（v3.1.0、MFT経路）を実行した結果を、Python `os.scandir` の独立走査とファイル単位で突き合わせた。
  - scan: 1,274,909 ファイル / 156.83GB。`fsutil volume allocationReport` のユーザーファイル割り当ては 183.3GB で、約26GB少ない。
  - **10,845 ファイルが size=0** と報告された（実サイズ合計 25.36GB）。例: Box のローテーションログ（0.3〜0.7GB）、`ProgramData\Microsoft\Search\Data\Applications\Windows\Windows.db`（1.0GB）、大きい `codex.exe` / `claude.exe`、TaskScheduler のクラッシュダンプ。
  - scan にしか現れないエントリ 11,610 件のうち、実ファイルは WinSxS・WindowsApps 等が **8.3 短縮名**（例 `AMDFAB~1.1_N`）で出力されたもの。
  - walk にしか現れないファイル 93,260 件 / 20.39GB。大半は**ハードリンク**の2本目以降（例: Edge / EdgeWebView / Copilot の `msedge.dll`）。
- 依頼: 「QuickFolderSizeのバグを調査して」
- 並行作業: 別セッションが同じ作業ツリー（`fix/mft-empty-path`）で「MFT経路で path が空になる」不具合を修正中。本調査では `src/` を編集しない。

## 調査結果

### 1. size=0（10,264〜10,845 件 / 約25GB）【バグ・確定】
- `ParseMftRecord`（src/engine/engine.cpp:305）が `base_record != 0` の拡張レコードを破棄している。`$ATTRIBUTE_LIST` を持つファイルでは `$DATA`（lowest_vcn=0、data_size）が拡張レコード側にあるため、size が 0 のまま残る。
- `fsutil file layout` で確認した。size=0 と報告された `Windows.db`（1.0GB、550エクステント）、`CachedExtensionVSIXs\openai.chatgpt-...`（440MB、346エクステント）、Chrome の `History`（63.6MB）は、いずれも `::$ATTRIBUTE_LIST` を持っていた。断片化の激しい大きいファイルや、EA 付きのファイルで起きる。
- 同じ理由で、Win32 名前空間の `$FILE_NAME` が拡張レコード側にあると、DOS 8.3 名で表示される（`AMDFAB~1.1_N` など、未検証の推定）。`$FILE_NAME` が1つもベースレコードに無いファイルは valid=false となり、ツリーから消える（walk にしか無くハードリンクでも仮想化でもない 5,988 件 / 1.99GB の一部。ただし、この件数にはスキャン後に作られたファイルも含まれる）。

### 2. ハードリンク（69,489 件 / 17.27GB）【仕様どおり・バグではない】
- walk 側は同じデータをリンクの数だけ数えている。MFT 経路は1レコード＝1回だけ数えるため、ディスク使用量としては正しい。
- 例: `msedge.dll`（332MB）は5本のリンクを持つ（Edge / EdgeCore\Optimized / EdgeWebView / EdgeCore / Copilot）。scan は名前空間の優先度が最も高い `EdgeCore\Optimized`（NTFS+DOS 名）にだけ計上している。
- 課題: どのフォルダに計上されるかは名前空間の優先度で決まり、ユーザーには分からない。

### 3. AppData\Roaming\Claude など（17,371 件 / 1.43GB）【walk 側の二重計上・バグではない】
- `AppData\Roaming\Claude\...\claude.exe` は、fsutil で開くと実体が `AppData\Local\Packages\Claude_pzs8sxrjxfjjc\LocalCache\Roaming\Claude\...` の同じファイル参照番号だった。MSIX のリダイレクトで同じ実体が2つのパスから見えており、walk が二重に数えていた。

### 4. 再解析ポイント付きファイルの一律除外【要確認】
- MFT 経路（engine.cpp:559）と Win32 経路（engine.cpp:694, 851）のどちらも、`FILE_ATTRIBUTE_REPARSE_POINT` 付きのファイルを除外している。コメント上の意図は「シンボリックリンクの除外」だが、OneDrive のクラウドファイルも再解析ポイントを持つ。
- オンラインのみのプレースホルダー（例 `jouhoutsushin2023.epub`: スパース、割り当て 0）は除外して問題ない。一方、ローカルにダウンロード済みのファイルもディスクを使っているのに除外される可能性がある。OneDrive 配下の差分は 0.80GB。未検証。
- CompactOS は無効（`compact /compactos:query`）のため、この PC では WOF 圧縮ファイルの除外は起きていない。
- 追加確認: OneDrive のルートフォルダ（`OneDrive - AISIN GROUP`）自体が再解析ポイント（クラウドタグ）を持つ。MFT 経路・Win32 経路のどちらも**OneDrive のツリーを丸ごと除外**している（scan 上の OneDrive は desktop.ini の 103 バイトだけ）。中身は通常ファイル 2 件、ローカル保持 50 件（0.01GB）、オンラインのみ 906 件（論理 0.80GB、割り当て 0）。**バグと判定**した（仕様書の除外の目的はジャンクション／シンボリックリンク対策）。

## 修正方針（2026-09-24 ユーザー指示「引き継いで全てバグをつぶして」）

別セッションで止まっていた path 空欄の修正（`include_paths=true`）を引き継ぎ、以下をまとめて直す。

1. **path 空欄**: 別セッションの変更（engine.cpp の `BuildEntryFromMft(..., true)`）を採用し、検証する。
2. **拡張レコード**: `base_record != 0` のレコードから、無名 `$DATA`（lowest_vcn=0 の data_size／resident の長さ）、`$FILE_NAME`（名前・親・名前空間）、`$REPARSE_POINT` のタグを取り出し、読み込み後にベースレコードへマージする。ベース参照のシーケンス番号が一致しないものは古いレコードとして捨てる。ファイルの有効判定（名前があるか）はマージ後に行う。これで 8.3 名の表示と、名前が拡張レコードにしか無いファイルの欠落も直る。
3. **再解析ポイント**: 除外するのは名前サロゲート（`IsReparseTagNameSurrogate`: シンボリックリンク、ジャンクション、マウントポイント、WSL シンボリックリンクなど）だけにする。クラウドファイル（OneDrive）、重複除去、WOF 圧縮などは集計に含める。MFT 経路ではタグを `$REPARSE_POINT`（0xC0）から読む。Win32 経路では `WIN32_FIND_DATAW::dwReserved0` から読む。タグが読めない場合は従来どおり除外する。
4. **オンラインのみのファイル**: `FILE_ATTRIBUTE_OFFLINE` / `RECALL_ON_OPEN` / `RECALL_ON_DATA_ACCESS` を持つファイルはローカルのディスクを使わないため、ファイル数には含め、サイズは 0 とする。
5. ハードリンクは従来どおり 1 回だけ数える（仕様どおり）。

## 検証項目
- `scripts/build.py` で GUI と CLI をビルドできること（自動テストは無い。UI の手動操作はしない）
- 昇格して CLI で C:\ をスキャンし、次を確認する: path が埋まる／size=0 誤報告が解消する（Windows.db 等）／8.3 名が消える／OneDrive 配下が集計される／合計が `fsutil volume allocationReport` のユーザーファイル割り当てに近づく
- 非管理者（Win32 経路）で OneDrive フォルダをスキャンし、除外されないこと、ジャンクションが引き続き除外されること

## 実装と結果

- `src/engine/engine.cpp`: `ParseMftRecord` がベース/拡張の両レコードから属性を取り出すよう変更し、`FinalizeMftNodes` で拡張レコードをマージ。再解析ポイントの判定を `IsSkippedReparse`（名前サロゲートのみ除外）に統一。非常駐の `$REPARSE_POINT` は先頭クラスタを読んでタグを取得。Win32 経路も `dwReserved0` のタグで同じ判定にした。
- `src/app/main_gui.cpp`: スキャン直後の直下1階層の仮表示も同じ判定にした（OneDrive の行が出ないのを防ぐ）。
- 途中で起きた後退と対処: オンラインのみ判定に `RECALL_ON_OPEN`（0x40000）を含めたところ、ディスク上では `FILE_ATTRIBUTE_EA` と同じビットのため、EA を持つ通常ファイル 66 万件（107GB）がサイズ 0 になった。判定から外して解消した。
- 途中で見つかった問題と対処: OneDrive 配下のフォルダは `$REPARSE_POINT` が非常駐（例: `Microsoft Teams チャット ファイル`、タグ 0x9000601a）で、常駐のタグだけを読んでいたため除外されていた。先頭クラスタを読むよう対応した。

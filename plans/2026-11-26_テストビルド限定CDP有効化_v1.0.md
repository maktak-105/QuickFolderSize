# 計画書: テスト用ビルドに限定したCDP(リモートデバッグ)有効化(v1.0)

## 依頼

2026-11-26、ユーザーから「案Bを進めて」との指示を受けた。
経緯は auto-window の `plans/2026-11-26_Playwright実アプリ疎通検証_結果_v1.0.md` を参照。

## 背景・現状分析

- auto-window の Playwright エンジンは、WebView2 アプリに CDP で接続して UI を自動テストする。
  CDP の有効化には、環境変数 `WEBVIEW2_ADDITIONAL_BROWSER_ARGUMENTS=--remote-debugging-port=N` を使っている。
- QuickFolderSize は管理者権限で動く(`EnsureAdministrator()`、`src/app/main_gui.cpp` L797-826)。
  WebView2 は、ホストが管理者権限で動いているとき、`WEBVIEW2_*` 環境変数とユーザー単位(HKCU)のレジストリ上書きを
  **仕様で無視する**(Microsoft Learn「WebView2 security best practices」)。2026-11-26 に実機でも確認済み
  (方式E・方式Rとも、msedgewebview2 のコマンドラインに `--remote-debugging-port` が付かなかった)。
- `createEnv(nullptr, userDataFolder, nullptr, ...)`(L912付近)は options を渡していない。
- `EnsureAdministrator()` の `ShellExecuteExW` は `lpParameters` を設定していない。そのため、管理者として起動し直すと
  起動引数がすべて失われる。現在 GUI 版は起動引数を使っていないので実害はないが、引数を使う機能を入れると問題になる。

## 方針

アプリが自分のコードで `ICoreWebView2EnvironmentOptions::AdditionalBrowserArguments` に引数を渡す。
コードからの指定は、管理者権限で動いていても有効になる。

**セキュリティ上の制約**: 管理者で動くアプリの CDP ポートが開いていると、同じ PC 上の管理者でないプロセスから、
管理者権限で動くページの JS を操作できてしまう(権限昇格の経路になる)。
そのため **CDP の受け付けはコンパイル時のマクロ `QFS_ENABLE_CDP` を定義したテスト用ビルドだけに限定する。**
配布版の `dist/QuickFolderSize.exe` には、CDP を受け付けるコード自体を含めない。

## 変更内容

1. **`src/app/main_gui.cpp`**
   - `EnsureAdministrator()`: `PathGetArgsW(GetCommandLineW())` で起動引数の部分を取り出し、`lpParameters` に渡す
     (全ビルド共通。起動引数を失わないようにするための修正)。
   - `#ifdef QFS_ENABLE_CDP` の中だけで、次を行う。
     - `ICoreWebView2EnvironmentOptions` を実装した最小限の COM クラス `QfsEnvOptions` を作る。
       `TargetCompatibleBrowserVersion` は SDK と同じ値 `151.0.4129.50` を返す。
     - `CommandLineToArgvW` で `--remote-debugging-port=N` を読む(N は 1024〜65535 の数字だけを受け付ける)。
       指定があれば `AdditionalBrowserArguments` に `--remote-debugging-port=N` を設定した options を `createEnv` に渡す。
       指定がなければ従来どおり nullptr を渡す。
     - デバッグログに `[CDP] enabled port=N` を出す。
   - リンクに `-lshlwapi` を追加する。
2. **`scripts/build.py`**
   - `--test-build` オプションを追加する。指定したときは `-DQFS_ENABLE_CDP` を付けて
     `build/test/QuickFolderSize_test.exe` を作り、`WebView2Loader.dll` もそこへコピーする。
     **配布用の `dist/` には一切出力しない。**
   - オプションなしのときの動作(dist へのビルド)は変えない。

## 検証

1. 通常ビルド: 従来どおり成功すること。`strings` で `remote-debugging-port` が exe に含まれないこと
   (CDP のコードが入っていないことの確認)。
2. テスト用ビルド: `build/test/QuickFolderSize_test.exe` ができること。
3. 実機(管理者で動作): auto-window から `exe_path` をテスト用 exe、`options.cdp_launch: arg` にして実行し、
   CDP 接続→スキャン→結果確認→スクリーンショットが成功すること。
   - 管理者でないプロセスから起動すると、アプリは管理者として起動し直す。この場合、起動したPIDはすぐ終了し、
     管理者で動く本体は管理者でない側から終了できない。そのため、実機検証は**管理者のターミナルで実行する**
     (ユーザーに依頼する)。
4. 通常ビルドの exe に `--remote-debugging-port` を付けて起動しても、CDP が開かないこと(配布版で無効になっていることの確認)。

## 変更しないもの

- スキャンエンジン、UI(HTML/JS)、CLI
- 配布版のバージョン番号(テスト専用機能であり、配布版の挙動は変わらないため)

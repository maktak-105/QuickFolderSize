# 計画書: JSONレポート出力・配布構成の見直し(v1.1)

v1.0からの変更点: 「B. engine_x64.dllを配布から外す」「C. index.htmlをEXEへ埋め込む」を追加。「A. JSONレポート出力」はv1.0のまま。v1.0は上書きせず保持。

## 目的

- **A**: スキャン結果をMarkdownに加えてJSONでも出力し、他ツール・スクリプトからの機械可読な利用を可能にする
- **B**: `engine_x64.dll`はGUI版に静的リンク済みでコード上どこからも参照されておらず、配布ZIPに含める意味がない死んだ成果物のため外す
- **C**: `index.html`は現状EXEと同じフォルダに置く実行時外部依存(見つからないとエラーダイアログで起動失敗)になっているため、EXEへリソースとして埋め込み依存を解消する。サイズはほぼ変わらない(現状もdist/binary配下に同梱している約90KBがEXE内部に移るだけ)

## 現状分析

### A. JSONレポート出力

v1.0記載のまま(変更なし)。要点のみ再掲:
- `static/js/app.js:555-590` の `generateMdReport()`/`onExportReport()` がMarkdown文字列を作り `export_report` コマンドでネイティブに渡す
- `core/native/webview_main.cpp:548` の `HandleExportReport()` は中身を見ずUTF-8で書き込むだけ(フォーマット非依存)
- 保存ダイアログの `COMDLG_FILTERSPEC`(`webview_main.cpp:320`)が `*.md` 固定

### B. engine_x64.dll

- `build_native.py:94-113`(「1. スキャンエンジンDLLをビルド」)で `engine.cpp` を単体で `-shared -static` コンパイルし、`dist/binary/engine_x64.dll` にコピーしている
- GUI本体(`build_native.py:116-136`)は `engine.cpp` を**直接ソースとしてstatic link**しており、このDLLをロード/リンクするコードはリポジトリ内に一切ない(grep済み: `.py`/`.cpp`/`.h`/`.bat`全て、参照は生成側のみ)
- `engine.h:2-3` のコメント「DLL(engine_x64.dll)としても、GUI/CLI実行ファイルへの静的リンクとしても同じソースからビルドされる」は将来のCLI版などを見越した設計だが、現状CLI版(`main_cli.cpp`)は未実装
- `.gitignore` は `core/native/*.dll` を既にGit管理外にしている(ビルド成果物であることは元々前提)

### C. index.html

- `build_native.py:71-72` で `bundle_html.py` が `templates/index.html` + `static/css/style.css` + `static/js/app.js` を1枚の自己完結HTML(`dist/binary/index.html`, 現状89047 bytes)にバンドル(**windres実行より前**に完了している。順序はこのまま利用できる)
- `webview_main.cpp:724-737`: 実行時に `exePath` と同じフォルダの `index.html` を `ReadUtf8FileToWString()` でディスクから読み、無ければ `templates\index.html` にフォールバック。どちらも無ければ `htmlContent` が空になり、`NavigateToString` 直前(850行目)でエラーダイアログを出す
- `windres` の実行時カレントディレクトリは `core/native`(`build_native.py:88` の `cwd=native_dir`)。現行の `.rc` の `IDI_ICON1 ICON "QuickFolderSize.ico"` / `RT_MANIFEST "QuickFolderSize.manifest"` も同じ流儀で、`core/native/` 直下のファイルを相対パスで参照している
- アイコンIDの扱いも先例があり、`QuickFolderSize.rc` の `#define IDI_ICON1 101` と同じ値が `webview_main.cpp:26` にも独立して `#define IDI_ICON1 101` と重複定義されている(共有ヘッダは無い)。新しいリソースIDも同じ流儀で揃える
- `build_native.py:157` で `templates/index.html`(バンドル前の開発用生HTML)を `dist/binary/templates/index.html` にもコピーしている。これは上記フォールバック専用で、埋め込み後は参照コードごと不要になる

### C. index.htmlをEXEへ埋め込む

1. **`bundle_html.py`**
   - `bundle(binary_dir)` が `dist/binary/index.html` を書き出した後、同じ内容を `core/native/index_embed.html` にもコピーする処理を追加(windresのカレントディレクトリ=`core/native`から相対参照するため)
2. **`core/native/QuickFolderSize.rc`**
   - `#define IDR_INDEX_HTML 201` を追加
   - `IDR_INDEX_HTML RCDATA "index_embed.html"` を追加(既存の`ICON`/`RT_MANIFEST`と同じ相対参照の流儀)
3. **`core/native/webview_main.cpp`**
   - 冒頭に `#define IDR_INDEX_HTML 201`(`.rc`と同じ値を独立定義、`IDI_ICON1`と同じ流儀)

   - 代わりに `FindResourceW(NULL, MAKEINTRESOURCEW(IDR_INDEX_HTML), RT_RCDATA)` → `LoadResource` → `LockResource` → `SizeofResource` でバイト列を取得し、`MultiByteToWideChar(CP_UTF8, ...)` で `std::wstring` に変換する関数(例: `LoadEmbeddedIndexHtml()`)を新設し、`ReadUtf8FileToWString(htmlFile)` の代わりに使う
   - リソース取得失敗時は、既存の「index.htmlの読み込みに失敗しました」エラーダイアログ文言を「埋め込みHTMLリソースの読み込みに失敗しました(ビルド不整合の可能性)」に修正して同様に表示

## 検証方法

1. `build.bat`が警告・エラーなく通ること。ビルドログで「エンジンDLLビルド」ステップが無くなっていること、`windres`が`index_embed.html`を正常に読み込んでいること
2. `dist/binary/`に`engine_x64.dll`が生成されないこと、`index.html`が(方針に応じて)生成されない/生成されても配布readmeの必須一覧に含まれないこと
3. `QuickFolderSize.exe`単体を`WebView2Loader.dll`のみと同じフォルダに置いて起動できること(`index.html`や`engine_x64.dll`を意図的に置かない状態でも正常起動する)
4. `QuickFolderSize_debug.log`のHTML読み込みログが埋め込みリソース経由に置き換わっていること(サイズが元の89047文字相当と一致)
5. スキャン・レポート出力(Markdown/JSON双方)・About表示・日英切替が従来通り動作すること(回帰確認)
6. `.rc`のリソースID重複や`windres`の相対パス解決に問題がないか、ビルドログのエラー有無で確認

## リスク

- **A(JSON)**: v1.0記載のまま。ノードごとの`path`有無の設計判断が未確定
- **B(DLL削除)**: 将来CLI版や外部ツールがこのDLLを前提にする計画があった場合、復元コストが発生する(ただし現状利用箇所ゼロを確認済みで、`git log`からの復元は容易)
- **C(HTML埋め込み)**:
  - `windres`の相対パス解決(`cwd=core/native`)に依存するため、`core/native/index_embed.html`が生成されないまま`build.bat`を実行するとリソースコンパイルが失敗する。`bundle_html.py`の呼び出し順序(GUIビルドより前)を崩さないことが前提
  - 開発中にHTML/CSS/JSを直接編集して`appDir\index.html`を差し替えるデバッグ手法(あれば)が使えなくなり、必ず`build.bat`再実行が必要になる(ただし現状もbundle_html.pyでの束ね直しが必須なので実質的な影響は小さい)
  - `RCDATA`は`windres`がバイト列としてそのまま埋め込むため、UTF-8前提の`MultiByteToWideChar`変換ロジックが`ReadUtf8FileToWString`と食い違うとエラーになる(検証4で文字数一致を確認)

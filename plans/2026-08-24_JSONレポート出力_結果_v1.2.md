# 実施結果 追記: レポート作成が実質フリーズする不具合の修正(v1.2)

対象: [結果v1.1](2026-08-24_JSONレポート出力_結果_v1.1.md)の続き。

## 経緯

「レポート作成が全く機能しない、JSONもMDも」→調査の過程で「作成中」トーストを追加したところ「さっきよりめっちゃ時間かかる」→ユーザーが実機で強制終了。

CLIで`C:\Windows`(約14.4万ファイル・19.3万ノード)を計測したところ、JSON化した文字列は56MBに達した。旧実装は、この規模の文字列をJS側で生成し`window.chrome.webview.postMessage`でネイティブへ丸ごと転送し、ネイティブ側は手書きのフラットJSONパーサ(`ExtractJsonString`、1文字ずつのエスケープ処理)で受け取る構造だったため、大きなツリーで実用不能なほど遅くなる(事実上フリーズする)ことが判明した。トースト表示自体が原因ではなく、既存のアーキテクチャの限界を初めて可視化しただけだった。

## 実施内容

`core/native/webview_main.cpp`:
- レポート本文の生成をJSからネイティブへ全面移管。`HandleExportReport(format, lang)`に変更し、`content`/`default_name`パラメータを廃止
- ネイティブはスキャン結果を保持している`g_prevRoot`から直接メモリ上でレポート文字列を組み立てる(WebMessage往復から巨大文字列を完全に排除)
- `BuildJsonReport()`: 既存の`SerializeEntryJson()`(scan_finishedで元々使っていた関数)を再利用してツリーをJSON化、メタ情報(path/scanned_at/total_size/subfolder_count/file_count_recursive)を付与
- `BuildMdReport()`/`RenderMdNode()`: JS版`generateMdReport()`と同じロジック(サイズ降順ソート、インデント階層、割合%、ファイル数)をC++へ移植。表示言語(`lang`)に応じて日英の見出し文言を切替
- `FormatSizeHuman()`/`FormatThousands()`: JSの`formatSize()`/`toLocaleString('en-US')`相当をC++で実装
- 保存ファイル名(`report_YYYYMMDD_HHMMSS.ext`)もネイティブ側で生成するよう変更

`static/js/app.js`:
- `generateMdReport()`/`generateJsonReport()`を削除(ネイティブ移管につき不要)
- `onExportReport(format)`は`{cmd:'export_report', format, lang: currentLang}`という小さいメッセージを送るだけに簡略化
- 生成処理が軽くなったため`setTimeout`での遅延実行は不要と判断し削除(「作成中」トーストは維持。ネイティブ処理+保存ダイアログの間、表示され続ける)
- 使われなくなった`report_h1`等12個のi18nキー、および元々未使用だった`report_title`キーを削除

`document/spec_jp.md`: 5節のWebMessageプロトコル表を新しい`export_report`パラメータ(`format`/`lang`のみ)に更新

## 検証結果

- `build.bat`成功(GUI 3,878,946 bytes / CLI 960,880 bytes、engine_x64.dllなし)
- コンパイルエラー1件を検出・修正: `(ja ? L"..." : L"...") + root.path`が`const wchar_t*`同士の加算になりコンパイル不可 → `std::wstring(root.path)`へ明示変換して解消
- `BuildJsonReport()`は実運用実績のある`SerializeEntryJson()`をそのまま再利用しているため、CLIのJSON出力(既にJSONパース検証済み)と同一ロジック
- `BuildMdReport()`はJS版のロジックを1行ずつ突き合わせて移植。ロジックの手動レビューのみで、実際の出力を動かして確認はしていない(GUIを起動していないため)

### 未検証

- 実際に大きいフォルダ(例: `C:\Windows`)でレポート作成が実用時間で完了するかは未確認。今回の変更で「巨大文字列がWebMessageを往復する」という主要因は排除したが、体感速度の最終確認はユーザー側での実施が必要
- `BuildMdReport()`が生成するMarkdownの見た目(絵文字・インデント・パーセント表示)の実機確認は未実施
- JSON/Markdownとも、大きいフォルダでの完了までの実測時間は取得していない

# QuickFolderSize の同期

## ユーザー指示（原文・2026-09-21）
- 「QuickFolderSize、なんか同期できないのでやってくれ」

## 解釈（確定ではない）
- 「同期」は、VS Code のソース管理の「変更の同期」、つまり、リモート（GitHub）との pull と push のこと。できない原因を調べ、同期できる状態にする。
- 原因が分かるまでは、履歴を書き換える操作（force push、reset --hard など）や、ユーザーの変更の破棄は行わない。

## 調査項目
1. リモートの設定、ブランチ、`origin` との先行・遅れ（fetch して最新の状態で確認する）。
2. 同期を止めうる要因: 未コミットの変更とリモートの変更の衝突、認証、ブランチの追跡設定、履歴の分岐、`.git` のロックなど。
3. 原因の特定 → 対処 → 同期の実行と確認。

## 調査で確認した事実（2026-09-21、実物）
- ローカルの `main` は `origin/main` より 1 コミット先（e68907c「.gitignore修正」、15:54、作者は `maktak-105`）。遅れは 0 件。中身は、`.gitignore` の追記 4 行（再編成で消えた規則を戻すもの）と、調査の計画書。作業ツリーの変更はこの計画書のほかに無い。ロックや、途中の操作（merge・rebase など）は無い。
- `git fetch --prune` は成功した。リモートで削除済みのブランチ 3 件（`agent/v2.1.1-json-cli-native-report`、`agent/version-v2`、`feature/mcp-server-v3.0.0`）が、ローカルの追跡から消えた。同期の失敗とは無関係。
- `git push --dry-run` は成功したが、これはサーバーの保護の判定まではしない。**実際の push は、GitHub に拒否された**: `remote rejected: main -> main (protected branch hook declined)`、`Changes must be made through a pull request.`
- `main` のブランチ保護（クラシック）: プルリクエスト必須、承認人数 0、必須の状態チェックなし、管理者にも適用（`enforce_admins`）、force push 禁止。過去の変更は、PR（#12、#13）のマージコミットで反映されている。
- リポジトリは PUBLIC。未 push のコミットの追加行に、個人のパス・メール・秘密の値は無いことを確認した。

## 原因（結論）
`main` は「PR 経由でしか変更できない」保護ブランチなのに、ローカルの `main` に直接コミット（e68907c）したため、push が拒否され、同期（pull と push）が完了しない状態になっていた。認証や履歴の分岐が原因ではない（遅れ 0、fetch は成功）。

## 対処
1. e68907c を指すブランチ `chore/gitignore-old-layout-leftovers` を作る（コミットは失わない）。
2. この計画書を、同じブランチの 2 つ目のコミットにする。
3. ブランチを push し、PR を作る。
4. PR を、マージコミット（過去の #12、#13 と同じ形式）でマージし、ブランチを削除する。承認と検査は不要な設定。保護の回避（管理者の強制マージ、保護の解除）はしない。
5. ローカルの `main` を `origin/main` に、fast-forward だけで追従させ、ローカルとリモートが一致することを確認する。

## 結果
- PR の番号とマージ後の状態は、Git の履歴（`Merge pull request #…`）と、この作業の報告に記す。
